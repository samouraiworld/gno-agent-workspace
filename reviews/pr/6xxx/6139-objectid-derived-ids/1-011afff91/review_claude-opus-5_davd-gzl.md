## Overview

A GRC20 token carries a text identifier that goes into every `Transfer`, `Approval`, `Mint` and `Burn` event it emits, and on master its tail is a number the creating realm picks, so one realm can give two independent ledgers the same identifier. This branch stops inventing identifiers and reads one the VM already keeps. Every stored object has an `ObjectID` of `PkgID` plus `NewTime`, and a new function hashes `objectid:<pkgid>:<newtime>` into a `g1…` address; a new native `chain/runtime.ObjectID(v)` returns it for the object behind `v`, and `Token.ID()` is that call. `grc20.NewToken` drops its `id seqid.ID` parameter, a token gains `TokenPath()` for the readable name and `OrigRealm()` for its issuer, every GRC20 event now carries both names, and `grc20reg` re-keys its entries by a slug the registering realm picks.

The derivation itself is right, and the branch's own evidence is unusually complete. The preimage is injective in `(PkgID, NewTime)`, separated from every other address family in the tree, unreachable by grinding, and the native reads without moving any realm clock; a stamped ID never moves; the generated bindings regenerate byte-identical; every bad input surfaces as a gno-recoverable exception; and the unstamped window is disclosed in the body, the ADR, three doc comments, the stdlib docs and two txtars. What follows sits on top of that, and the one live defect is not in the derivation.

**Verdict: REQUEST CHANGES** — two `grc20.Token` values held in one struct or one array report the same `ID()` while carrying two independent ledgers, which is the ambiguity [issue 6026](https://github.com/gnolang/gno/issues/6026) exists to remove reached through a different door, and the branch ships the opposite claim written in three places (4 Warnings, 1 Missing test, 7 Nits, 2 Suggestions).

## Summary

The load-bearing function is one line, [`misc.go:219`](https://github.com/gnolang/gno/blob/011afff91/gnovm/pkg/gnolang/misc.go#L219) · [↗](../../../../../.worktrees/gno-review-6139/gnovm/pkg/gnolang/misc.go#L219), and it is injective in its two inputs: [`PkgID.String()`](https://github.com/gnolang/gno/blob/011afff91/gnovm/pkg/gnolang/realm.go#L74-L76) · [↗](../../../../../.worktrees/gno-review-6139/gnovm/pkg/gnolang/realm.go#L74-L76) is the fixed string `RID` plus exactly 40 hex characters, so the second colon always falls at the same byte, and `strconv.FormatUint` emits no leading zeros. Landing on one chosen address costs 2^160 hashes and landing on any of the roughly 10^7 addresses a chain already holds costs about 2^137, so grinding is not a route. The defect is one layer up, in [`X_objectID`](https://github.com/gnolang/gno/blob/011afff91/gnovm/stdlibs/chain/runtime/native.go#L54-L66) · [↗](../../../../../.worktrees/gno-review-6139/gnovm/stdlibs/chain/runtime/native.go#L54-L66): it resolves a value to an object through [`TypedValue.GetFirstObject`](https://github.com/gnolang/gno/blob/011afff91/gnovm/pkg/gnolang/ownership.go#L415-L420) · [↗](../../../../../.worktrees/gno-review-6139/gnovm/pkg/gnolang/ownership.go#L415-L420), which for a pointer answers with the container the pointer points into and for a slice with the backing array.

Two more things sit outside the derivation. The new gas row is a flat 200 on a consensus path, priced against `getSessionInfo`, which does no hashing, where the calibrated row doing the same work charges 908. And the package that owns the derivation pins no address of its own: an edit to the preimage prefix or to the `PkgID` flag nibble reddens the two txtars this diff adds and leaves all three unit tests beside the function green.

## Fix

`Token.id` and its `seqid.ID` constructor argument are gone. [`Token.ID()`](https://github.com/gnolang/gno/blob/011afff91/examples/gno.land/p/demo/tokens/grc20/token.gno#L145-L147) · [↗](../../../../../.worktrees/gno-review-6139/examples/gno.land/p/demo/tokens/grc20/token.gno#L145-L147) is now a native call returning the object's derived address, [`TokenPath()`](https://github.com/gnolang/gno/blob/011afff91/examples/gno.land/p/demo/tokens/grc20/token.gno#L153-L155) · [↗](../../../../../.worktrees/gno-review-6139/examples/gno.land/p/demo/tokens/grc20/token.gno#L153-L155) carries the readable `rlmPath.symbol` the old identifier used to hide, and every event carries both. The load-bearing constraint is that `NewTime` is stamped only when the owning realm writes its objects out, which happens as a realm frame returns, so a token's address does not exist during the call that creates it; [`grc20reg.Register`](https://github.com/gnolang/gno/blob/011afff91/examples/gno.land/r/demo/defi/grc20reg/grc20reg.gno#L55) · [↗](../../../../../.worktrees/gno-review-6139/examples/gno.land/r/demo/defi/grc20reg/grc20reg.gno#L55) works around that by writing its entry through an explicit same-realm cross, whose return runs the write-out pass before the event is emitted.

## Verified

- The preimage is injective in its two inputs and separated from every other address family in the tree. `PkgID.String()` is `RID` plus exactly 40 hex characters, so the separator is unambiguous, and `strconv.FormatUint` emits no leading zeros. Ten `AddressFromPreimage` call sites exist in the tree, carrying six other preimage shapes. The two `pkgPath:` shapes differ at byte 0; the three collector names are the fixed strings `fee_collector`, `inert_charge_collector` and `storage_fee_collector`; the multisig preimage is an amino `Any` beginning `0a 12 2f "tm.PubKey"`. The two remaining pubkey derivations do not use that function at all: ed25519 hashes a 32-byte pubkey where the shortest object preimage is 54 bytes, and secp256k1 is RIPEMD160 over SHA256. Grinding to one chosen address costs 2^160 and to any of the roughly 10^7 addresses a chain holds about 2^137.
- The native reads and never writes. [`TestObjectID`](https://github.com/gnolang/gno/blob/011afff91/gnovm/stdlibs/chain/runtime/native_test.go#L284-L293) · [↗](../../../../../.worktrees/gno-review-6139/gnovm/stdlibs/chain/runtime/native_test.go#L284-L293) asserts `m.Realm.Time` is unchanged across every read, and a stamped ID never moves afterwards because [`assignNewObjectID`](https://github.com/gnolang/gno/blob/011afff91/gnovm/pkg/gnolang/realm.go#L1988-L1990) · [↗](../../../../../.worktrees/gno-review-6139/gnovm/pkg/gnolang/realm.go#L1988-L1990) panics on a re-stamp.
- A foreign realm stamping a token cannot collide with the owning realm's own later ticks: `touchForeignRealm` goes through `store.GetRealmByID`, which returns the same cached `*Realm` pointer the machine already holds, so there is one counter and no reuse.
- VM-fault recoverability holds across 15 input shapes driven through the native inside a gno `recover()` at this head, [`tests/zz_objectid_recover.gno`](tests/zz_objectid_recover.gno): every bad input surfaces as `value has no object identity` through `m.PanicString`, and no bare Go panic escaped. `GetFirstObject`'s two bare Go panics, on [`RefValue{PkgPath}`](https://github.com/gnolang/gno/blob/011afff91/gnovm/pkg/gnolang/ownership.go#L439) · [↗](../../../../../.worktrees/gno-review-6139/gnovm/pkg/gnolang/ownership.go#L439) and on a [heap item](https://github.com/gnolang/gno/blob/011afff91/gnovm/pkg/gnolang/ownership.go#L448) · [↗](../../../../../.worktrees/gno-review-6139/gnovm/pkg/gnolang/ownership.go#L448), were probed independently by two lenses and reached by neither, and no construction was found that reaches either; that is why no finding claims they are reachable.
