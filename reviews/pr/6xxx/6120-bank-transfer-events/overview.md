# Bank transfer events for ugnot movements

Generated by claude-opus-5.

## TLDR

A gno.land node reports what a transaction did through two channels: the message
itself, which anyone can read off the signed transaction, and the event list in
the transaction result. Moving ugnot used to write balances and say nothing in
either channel unless the message happened to describe the move. This change
makes the bank keeper announce every transfer it performs, so a service that
rebuilds account balances by reading transactions can see the moves it could not
see before.

## The problem

Four things move ugnot between accounts on gno.land.

| Move | Visible before this change? |
| --- | --- |
| `bank.MsgSend` | Yes. Sender, recipient and amount are fields on the message. |
| `bank.MsgMultiSend` | The message type carries the inputs and outputs, but it was not registered with the amino encoder, so a node refused to decode one. |
| A realm calling `banker.SendCoins` | No. The addresses and the amount are decided while the contract runs. |
| The `-send` envelope on `maketx call`, `run` and `addpkg` | Partly. The amount is on the message, and nothing records where the realm forwards it next. |

[GnoScan](https://gnoscan.io) is the service that motivated the change. It builds
its account balance table the way it handles GRC20 tokens, by reading transaction
results and events, so a balance change with no event is a balance change it
never learns about.

## What an event is here

An event in Tendermint2 is an ordinary Go value satisfying the
[`abci.Event`](https://github.com/gnolang/gno/blob/23e9de5ad/tm2/pkg/bft/abci/types/types.go#L212-L214)
interface, registered with the amino encoder and appended to a per-transaction
list held on the SDK context. The GnoVM already uses that list for `chain.Emit`
and for its storage deposit notices. This change adds two more values to it.

```go
type TransferEvent struct {
	From  string    `json:"from"`
	To    string    `json:"to"`
	Coins std.Coins `json:"coins"`
}

type MultiTransferEvent struct {
	Inputs  []Input  `json:"inputs"`
	Outputs []Output `json:"outputs"`
}
```

## Where they are emitted

Every one-to-one move funnels through one unexported function,
[`BankKeeper.sendCoins`](https://github.com/gnolang/gno/blob/23e9de5ad/tm2/pkg/sdk/bank/keeper.go#L173-L193),
so a single emit there covers the message handler, the realm banker and the send
envelope alike.

```mermaid
flowchart LR
  A["bank.MsgSend"] --> S
  B["realm banker.SendCoins"] --> S
  C["-send envelope on call, run, addpkg"] --> S
  S["BankKeeper.sendCoins"] --> E1["TransferEvent"]
  D["bank.MsgMultiSend"] --> M["BankKeeper.InputOutputCoins"]
  M --> E2["MultiTransferEvent"]
```

A multisend pools several senders and pays out to several recipients, and the
totals are all that must match. There is no truthful way to say which sender
funded which recipient, so the change publishes the whole batch as one event
carrying the original input and output lists rather than inventing pairs.

## What the reader sees

Both rows below encode the same `TransferEvent`. The first is what an RPC client
receives, since every RPC response passes through
[`amino.MarshalJSON`](https://github.com/gnolang/gno/blob/23e9de5ad/tm2/pkg/bft/rpc/lib/types/types.go#L207).
The second is what `gnokey` prints on its `EVENTS:` line, which uses the standard
library encoder through
[`ResponseBase.EncodeEvents`](https://github.com/gnolang/gno/blob/23e9de5ad/tm2/pkg/bft/abci/types/types.go#L124-L132).

| Encoder | Output |
| --- | --- |
| amino, over RPC | `[{"@type":"/bank.TransferEvent","from":"g1from","to":"g1to","coins":"7ugnot"}]` |
| `EncodeEvents`, in `gnokey` | `[{"from":"g1from","to":"g1to","coins":[{"denom":"ugnot","amount":7}]}]` |

The two differ because `std.Coins` carries a
[`MarshalAmino`](https://github.com/gnolang/gno/blob/23e9de5ad/tm2/pkg/std/coin.go#L216-L218)
method rendering it as a single string, and the standard library encoder does not
call that method. Both rows are the output of
[`tests/event_wire_shapes_test.go`](https://github.com/samouraiworld/gno-agent-workspace/blob/main/reviews/pr/6xxx/6120-bank-transfer-events/1-23e9de5ad/tests/event_wire_shapes_test.go).

## What stays silent

Two kinds of ugnot movement keep no transfer event.

Gas fees leave the payer through
[`SendCoinsUnrestricted`](https://github.com/gnolang/gno/blob/23e9de5ad/tm2/pkg/sdk/bank/keeper.go#L161-L165),
which skips the transfer policy and emits nothing. The amount is on the
transaction as `gas_fee`.

Storage deposits move ugnot between the payer and an address derived from the
realm path, again through `SendCoinsUnrestricted`. Those already have their own
`StorageDepositEvent` and `StorageUnlockEvent`, which carry the amount and the
package path but not the two addresses.

## Concepts

<details><summary>Why events sit inside the block header</summary>

The event list is not a log. A node folds each transaction's `Error`, `Data` and
`Events` into an
[`ABCIResult`](https://github.com/gnolang/gno/blob/23e9de5ad/tm2/pkg/bft/types/results.go#L14-L18),
merkle-hashes the set, and writes the root into the next block header as
[`LastResultsHash`](https://github.com/gnolang/gno/blob/23e9de5ad/tm2/pkg/bft/state/execution.go#L456).
Every node then checks that field against
[its own execution](https://github.com/gnolang/gno/blob/23e9de5ad/tm2/pkg/bft/state/validation.go#L82-L86).
So the set of events a transaction produces is agreed on by the whole network,
the same way balances are.
</details>

<details><summary>What happens to events when a message fails</summary>

The events accumulate on one list for the whole transaction, created fresh in
[`BaseApp.runMsgs`](https://github.com/gnolang/gno/blob/23e9de5ad/tm2/pkg/sdk/baseapp.go#L686-L687).
That list is copied into the result
[only when every message succeeded](https://github.com/gnolang/gno/blob/23e9de5ad/tm2/pkg/sdk/baseapp.go#L737-L739),
so a transfer whose transaction later fails leaves no event behind, matching the
balance write that also rolls back.
</details>
