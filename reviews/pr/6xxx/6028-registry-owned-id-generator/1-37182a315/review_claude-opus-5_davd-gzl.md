**TL;DR:** Today a GRC20 token's identifier is a number the creating realm picks itself, so a realm that picks the same number twice ends up with two different tokens announcing the same identifier in their events. This PR moves the numbering to a single counter owned by the token registry, and makes the registry refuse any token that did not get its identifier from that counter.

**Verdict: NEEDS DISCUSSION** — the design works end to end, but it hands every realm a writable handle on the registry's own state, the uniqueness it advertises is a convention rather than a check, and it rewrites the same `Register` function as [PR 6027](https://github.com/gnolang/gno/pull/6027) in an incompatible way, so a maintainer has to pick an order before either can land (6 Warnings, 5 Nits, 3 Missing tests, 2 Suggestions).

## Summary

`Token.ID()` is what a token puts in its `Transfer`, `Approval`, `Mint` and `Burn` events, and on master its trailing component is a `seqid.ID` the creating realm supplies. Nothing stops a realm passing the same value twice, and the four shipped single-token realms all pass a literal `0`, so two tokens can announce the same identity. The PR adds [`p/onbloc/identifier`](https://github.com/gnolang/gno/blob/37182a315/examples/gno.land/p/onbloc/identifier/identifier.gno#L1-L72) · [↗](../../../../../.worktrees/gno-review-6028/examples/gno.land/p/onbloc/identifier/identifier.gno#L1-L72), a `Generator` bound to its realm's package path that hashes `packagePath:height:sequence` into a 13-character Crockford base32 code; `grc20reg` constructs one at init, hands it out through [`IdentifierGenerator()`](https://github.com/gnolang/gno/blob/37182a315/examples/gno.land/r/demo/defi/grc20reg/grc20reg.gno#L27-L29) · [↗](../../../../../.worktrees/gno-review-6028/examples/gno.land/r/demo/defi/grc20reg/grc20reg.gno#L27-L29), and [`Register`](https://github.com/gnolang/gno/blob/37182a315/examples/gno.land/r/demo/defi/grc20reg/grc20reg.gno#L58-L60) · [↗](../../../../../.worktrees/gno-review-6028/examples/gno.land/r/demo/defi/grc20reg/grc20reg.gno#L58-L60) rejects any token whose `IdentifierPath()` is not that generator's. Separately the registry stops keying by `realm.symbol` and keys by a caller-chosen `realm.slug` alias instead, which is the same rekey [PR 6027](https://github.com/gnolang/gno/pull/6027) makes.

The cross-realm mechanism is real and verified live: `grc20factory.New` called post-genesis mutates `grc20reg`'s persisted generator through borrow rule #2, and the tx receipt shows the storage diff landing on `gno.land/r/demo/defi/grc20reg`. What is not real is the uniqueness guarantee the `identifier` package doc states. It is per-Generator, not per-realm, and holds for registered tokens only because `grc20reg` happens to build exactly one Generator.

Reading order: `p/onbloc/identifier/identifier.gno`, `p/demo/tokens/grc20/token.gno`, `r/demo/defi/grc20reg/grc20reg.gno`, then the four call-site realms, then the tests and txtars.

## Diagram

```
  /r/demo/defi/foo20                    /r/demo/defi/grc20reg
  ┌────────────────────┐                ┌──────────────────────────┐
  │ init(cur realm)    │                │ idGenerator *Generator   │  owned here
  │                    │  ①  IdentifierGenerator()                 │
  │  gen := ───────────┼───────────────▶│  return idGenerator      │  raw pointer out
  │                    │                └──────────────────────────┘
  │  grc20.NewToken(   │
  │    ..., gen, cur)  │  ②  gen.NextID()   ◀── borrow rule #2:
  │                    │      writes gen.sequence and gen.latestHeight
  │                    │      under grc20reg's realm, from foo20's frame
  │                    │
  │  grc20reg.Register(cross(cur), Token, "")
  └────────┬───────────┘  ③  checks Token.IdentifierPath() == "…/grc20reg"
           │
           ▼
   registry[rlmPath + "." + slug] = token      ◀── the diff changes this key
```

Edge ① is the leak: any realm, not just a token realm, can take that pointer and drive edge ② without ever reaching edge ③.

## Fix

`NewToken` swaps its `id seqid.ID` parameter for `gen *identifier.Generator`, builds the id as `pkgPath + "." + symbol + "." + gen.NextID()` and records `gen.PackagePath()` in the new [`identifierPath`](https://github.com/gnolang/gno/blob/37182a315/examples/gno.land/p/demo/tokens/grc20/types.gno#L92-L93) · [↗](../../../../../.worktrees/gno-review-6028/examples/gno.land/p/demo/tokens/grc20/types.gno#L92-L93) field, exposed as `IdentifierPath()`. `Register` swaps its `realm.symbol` prefix assertion for a bare [`rlmPath + "."` prefix](https://github.com/gnolang/gno/blob/37182a315/examples/gno.land/r/demo/defi/grc20reg/grc20reg.gno#L53) · [↗](../../../../../.worktrees/gno-review-6028/examples/gno.land/r/demo/defi/grc20reg/grc20reg.gno#L53) plus the issuer equality check, and keys the tree by `fqname.Construct(rlmPath, slug)`. The load-bearing constraint is that only `grc20reg` can construct a `Generator` carrying `grc20reg`'s package path, because [`NewGenerator`](https://github.com/gnolang/gno/blob/37182a315/examples/gno.land/p/onbloc/identifier/identifier.gno#L32-L46) · [↗](../../../../../.worktrees/gno-review-6028/examples/gno.land/p/onbloc/identifier/identifier.gno#L32-L46) reads the path off a live `IsCurrent` frame and the field is unexported.

- **[any realm can write registry state]** `examples/gno.land/r/demo/defi/grc20reg/grc20reg.gno:27-29` — `IdentifierGenerator()` returns a raw pointer to `grc20reg`'s persisted generator, so any realm can drive its mutation methods with `grc20reg`'s own authority.
  <details><summary>details</summary>

  This is the shape [§8 of the contract review guide](https://github.com/gnolang/gno/blob/37182a315/docs/resources/gno-ai-contract-review.md?plain=1#L90-L113) · [↗](../../../../../.worktrees/gno-review-6028/docs/resources/gno-ai-contract-review.md#L90-L113) names as a write-authority leak: a `/p/` type whose fields are all unexported but whose exported method writes to the receiver, returned as a pointer to an instance stored in the realm. [`NextID`](https://github.com/gnolang/gno/blob/37182a315/examples/gno.land/p/onbloc/identifier/identifier.gno#L55-L72) · [↗](../../../../../.worktrees/gno-review-6028/examples/gno.land/p/onbloc/identifier/identifier.gno#L55-L72) writes `g.latestHeight` and `g.sequence`; borrow rule #2 fires on method entry because the object was allocated in `grc20reg`, so the write commits.

  Verified live: a four-line realm that calls `grc20reg.IdentifierGenerator()` and loops `NextID()` fifty times, creating no token and registering nothing, succeeds and the tx receipt carries `{"bytes_delta":10,…,"pkg_path":"gno.land/r/demo/defi/grc20reg"}`. The reachable damage is bounded, since the only mutations are a monotonic counter and a height watermark, so the storage bump tops out around the varint width of a `uint64` and the attacker pays for it. What is not bounded is the principle: `grc20reg` cannot rate-limit, audit or revoke use of its own id sequence, and every future method added to `Generator` becomes callable by anyone under `grc20reg`'s authority. Fix: keep `idGenerator` unexported and expose issuance as a crossing function on `grc20reg` that returns only the code, so the pointer never leaves the realm.
  </details>
