Bounding gno's test memory by memory, not by core count

Explainer for gnolang/gno#6061. Generated by claude-opus-5.

The problem

Three of gno's test suites decide how many workers to run from the number of CPU cores, through GOMAXPROCS, which is what go test uses as the default parallelism. Each worker in these particular suites is expensive in memory rather than in CPU: a gno.land integration script runs a whole node with its own store, its stdlib byte cache and its genesis write batch, and a GnoVM filetest worker holds a store retaining the parsed and evaluated form of every package its tests have touched.

So peak memory tracks the core count of whoever runs the suite. The GitHub-hosted runners have four cores, which is the size these suites are implicitly tuned for, and a sixteen-core workstation quadruples every one of them. The suites keep getting bigger long after they stop getting faster.

What the change does

It caps the expensive thing in each suite rather than the parallelism, so nobody's -parallel flag is overridden. Two of the three take a static cap; the third takes a controller that reads the machine.

SuiteWhat is cappedHow the cap is chosen
GnoVM filetests, TestFiles the pool of VM stores, fixed at construction static: the smaller of the core count and four
examples, through its Makefile gno test workers, one store each static: the literal 4, passed as -p
gno.land integration, the txtar scripts nodes running at once, started one at a time a live allowance that ramps against free memory

The controller, in one table

The allowance starts at the static cap, the count CI validates, and moves by one step at a time. Three quantities decide each step: the memory the reading reports as available, a reserve left to the rest of the system, and the cost of one more node.

ConditionStepWhy
available is under the reserve, and the allowance is above the floorallowance minus onethe memory being measured is shared, so a browser or a second suite starting should cost this run its ramp rather than cost the machine
available covers the reserve plus a whole further node, every slot is taken, and the allowance is under the ceilingallowance plus onegrowing only when saturated avoids overshooting while admitted nodes are still filling out
anything between the twounchangedthe gap between the thresholds is what stops the allowance oscillating
less than one second since the last readingunchanged, and no reading takena blocked script polls five times a second, and a reading costs a subprocess on darwin

How this page's simulator was checked

The JavaScript above mirrors the controller's step rule line for line. It was run against the six controller cases the pull request itself adds, floor, ramp, hysteresis band, shrink under pressure, static fallback and release, with the same inputs and the same expected allowances. All six agree with the Go implementation; the mirror is what this page's numbers come from.
