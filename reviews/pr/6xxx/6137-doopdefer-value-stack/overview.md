# PR 6137: `defer f(g())` bound the wrong function

Generated by claude-opus-5.

## Concepts

The GnoVM evaluates a call by pushing values onto one shared value stack: the
function value first, then each argument. `doOpDefer` reads that stack when it
records a deferred call, and it has to know how many argument values sit above
the function value to reach it.

Go lets a single multi-value call stand in for a whole argument list. `g()`
returning two results can be written `f(g())` where `f` takes two parameters.
The gno preprocessor records both counts on every `CallExpr`:

| Field | Meaning | `f(a, b)` | `f(g())`, `g` returning two |
| --- | --- | --- | --- |
| `len(Args)` | syntactic arguments written in source | 2 | **1** |
| `NumArgs` | argument *values* the stack will hold | 2 | **2** |

`NumArgs` is computed by `countNumArgs`, which returns `len(Args)` for every
call except the one-argument spread form, where it returns the result count of
the inner call.

## What went wrong

`doOpDefer` used `len(Args)`. For `defer f(g())` the stack holds three values
and the code looked two down instead of three.

```
value stack after the defer statement evaluates its operands:

    index from top:      3        2        1
                      [  f  ][   r0   ][   r1   ]   <- top
```

`PeekValue(n)` counts from the top, so the function value is at
`PeekValue(numArgs + 1)`.

Before (`numArgs = len(Args) = 1`):

```
    PeekValue(1 + 1) = PeekValue(2) = r0     <- an argument, not the function
```

After (`numArgs = NumArgs = 2`):

```
    PeekValue(2 + 1) = PeekValue(3) = f      <- the function
```

The value that `doOpDefer` picked up was then switched on by its runtime kind,
which is what made the same bug produce two different symptoms.

| `r0` is | Branch taken | Observed |
| --- | --- | --- |
| an `int` (`defer h(twovals())`) | `case nil`, because an `int`'s `.V` is nil | `runtime error: defer called a nil function` |
| a `func` value (`defer f(g())`) | `case *FuncValue` | the wrong function runs, and `f` never does |

The second row is the sharper one: the program did not fail, it silently ran a
value that happened to be an argument.

## The fix

One line, plus one line in a neighbouring branch.

`numArgs` now reads `ds.Call.NumArgs`, the count the preprocessor already
computed. The ordinary call path in `doOpPrecall` has always read `cx.NumArgs`
for the same purpose, so this makes defer agree with call rather than
introducing a new source of truth.

The `case nil` branch, reached when a genuinely nil func value is deferred
(`var nf func(int, int); defer nf(1, 2)`), pushed the deferred entry and popped
only the function value, leaving the evaluated arguments behind. It now discards
them with `PopValues(numArgs)`, matching the two branches above it. That leak
was never observable: a call frame truncates the value stack back to its
recorded height when it returns, so the strays were dropped before anything
read them.

## Behaviour, before and after

Against `go run` on the same source, which is the reference:

| Source | Go | gno before | gno after |
| --- | --- | --- | --- |
| `defer h(twovals())` | `h: 15` | panic, `defer called a nil function` | `h: 15` |
| `defer f(g())`, `g` returning `(func(), int)` | `f: n = 99` | `WRONG: marker ran` | `f: n = 99` |
| `defer variadic(two())` | runs `variadic` | panic | runs `variadic` |
| `defer counter{n: 1}.add(two())` | runs the method | panic | runs the method |
| `defer println(two())` | `7 8` | panic | `7 8` |
| `defer nf(1, 2)`, `nf` nil | call-of-nil at the deferred call | same | same |

Only the spread form moves. `NumArgs` equals `len(Args)` for every other call,
so an ordinary `defer` behaves identically on both sides of the change.
