What PR 6082 changes: the lock-free query connection

An explainer for gnolang/gno pull request 6082. Generated by claude-opus-5. No review findings on this page.

A gno.land node talks to its own application over three ABCI connections. This pull request removes the lock from one of them. Everything below is background for reading that diff.

The three connections

Tendermint2 opens three separate ABCI clients against the same in-process application. They exist so that different kinds of traffic do not interfere with one another.

ConnectionWho drives itWhat it calls
consensusthe block executorBeginBlock, DeliverTx, EndBlock, Commit
mempooltransaction intakeCheckTx
querythe RPC server, one goroutine per HTTP requestEcho, Info, Query

All three are the same Go type, abcicli.localClient, and each one holds a Locker that it takes around every call into the application. Which Locker each connection holds is the entire subject of this change.

Three states of the world

  before PR 5431
  consensus ─┐
  mempool   ─┤── one shared mutex ──> Application
  query     ─┘        a slow simulate stalls block production

  after PR 5431
  consensus ─┐
  mempool   ─┴── mtx ──────────────> Application
  query     ──── queryMtx ─────────> Application
                 queries no longer stall consensus,
                 but still run one at a time among themselves

  after PR 6082 (this change)
  consensus ─┐
  mempool   ─┴── mtx ──────────────> Application
  query     ──── noLock ──────────> Application
                 every query goroutine enters together

The mechanism is small. localClient.mtx changes type from *sync.Mutex to the sync.Locker interface, and the query connection is handed a noopMutex whose Lock and Unlock have empty bodies. No method body changes.

The trade. A lock is a fact the compiler enforces. An invariant is a promise a human keeps. This change replaces the first with the second: every piece of state reachable from Application.Query and Application.Info must now be safe for several goroutines at once, because nothing serialises them any more.

What a query actually touches

"A query" is not one path. BaseApp.Query dispatches on the first path segment, and the three branches reach very different amounts of machinery.

PathExampleWhere the state comes from
.app/*.app/simulateRuns a transaction without committing it. Above block height 1 it pins an immutable snapshot; below it, it falls back to the shared checkState.
.store/*.store/main/keyReads the committed multistore through a frozen snapshot, with a live-store fallback when no snapshot view exists at that height.
anything elsevm/qrender, vm/qeval, auth/accounts/…Routed to a keeper. The vm routes build a GnoVM machine and interpret realm code.

The isolation machinery, and where it stops

PR 5431 built most of what parallel queries need. It is worth knowing what each piece isolates, because the pieces do not all cover the same thing.

MechanismWhat it makes per-query
MultiImmutableCacheWrapWithVersionA frozen, reference-counted database snapshot, so a concurrent Commit cannot move the ground under a running query.
defaultStore.BeginTransactionFresh cacheObjects, cacheTypes and cacheRealms maps, and a forked allocator, per call.
lastBlockHeaderAn atomic.Pointer, so reading the current header never races a block.
cacheNodesShared. The transaction store wraps the parent map rather than copying it, and a query never writes back through it.

That last row is the interesting one. Reaching the parent map is how a query finds the PackageNode for a deployed realm without re-reading it from disk. It also means the Type objects hanging off those nodes are one set of objects shared by the whole process — including by block execution.

Why shared types matter here

The GnoVM computes some properties of a type once and remembers the answer on the type itself. Two examples:

func (ft *FuncType) BoundType() *FuncType {
    if ft.bound == nil {                       // read
        ft.bound = &FuncType{                  // write
            Params:  ft.Params[1:],
            Results: ft.Results,
        }
    }
    return ft.bound
}

This is a cache: cheap the first time, free afterwards. It is also a read followed by a write with nothing in between, which is safe only if one goroutine at a time can be inside it. Under the old lock, exactly one could. TypeID has the same shape, and interface satisfaction is decided by comparing TypeID values.

The pre-first-block window

One branch of Simulate does not use a snapshot at all:

header := app.getLastBlockHeader()
if header == nil || header.GetHeight() < 1 {
    ctx := app.getContextForTx(RunTxModeSimulate, txBytes)   // shared checkState
    return app.runTx(ctx, txBytes)
}

The window is easy to underestimate. InitChain builds its header with no Height field set, and Commit republishes whatever header it was handed — so committing genesis does not leave this branch. It closes at the first real BeginBlock.

How long that takes depends on a consensus setting. With CreateEmptyBlocks at its default of true, block 1 arrives on a timer. With it set to false, the node waits for a transaction before producing any block at all — and both gnodev and the in-memory integration node set it to false.
