What PR 6110 changes: every string gets a serial number

An explainer for gnolang/gno pull request 6110. Generated by claude-opus-5. No review findings on this page.

The GnoVM puts a ceiling on how much memory one transaction may hold at once. It does not track that total incrementally forever: it rebuilds it from scratch at each garbage collection, by walking every value the program can still reach and adding up their sizes. This pull request is about strings, which the walk had been getting wrong in three different directions at the same time.

Concepts

Three words carry the whole change. They are worth pinning down before anything else.

  • Backing. A Go string is two machine words: a pointer to some bytes, and a length. The bytes themselves are the backing. Two strings can point into the same backing, and slicing one with s[2:5] makes a second string over the same bytes rather than copying them.
  • Recount. The garbage collector's walk. It starts the total at zero and adds the size of each reachable value. Whatever it fails to add is memory the program holds for free; whatever it adds twice is memory the program is billed for twice.
  • Mint. The moment the VM creates a string through its allocator, Allocator.NewString. This pull request makes that moment the thing a string is identified by.

The three ways strings broke the recount

  1. a string loaded back from the store was never counted

     fillTypesOfValue(...) saw a string and returned it untouched,
     so its bytes were invisible to the recount forever.


  2. two strings over one backing were each billed for all of it

     s  = "aaaa...."  (1052 bytes)         recount: 48 + 1052
     s1 = s           (same backing)       recount: 48 + 1052   the same
                                                                 1052 bytes,
                                                                 billed twice

  3. a slice was billed as if it had copied

     s2 = s[1:11]     (10 bytes, no copy)  charged: 48 + 10 bytes it
                                                          never allocated

Bugs 2 and 3 pull in opposite directions, which is why neither shows up as a simple offset. A program that copies strings is overcharged, a program that loads them from storage is undercharged, and a program that slices is charged for a copy that never happened.

The one hard question

Every fix for bug 2 has to answer the same question at recount time:

Standing in front of a string, having already added some bytes to the total: did I already count this backing?

Answering it needs a name for the backing that stays the same across every string sharing it, and differs between backings. Four designs have been proposed for gno, and they differ only in where that name is kept.

DesignThe name of a backing isWhat that costs
PR 5082 nothing, only a flag saying "this value owns its backing" A flag cannot name anything, so the question stays unanswerable: a copy either re-owns the backing and it is counted twice, or it does not and a surviving slice counts it zero times.
PR 4885 the address range the Go runtime placed the bytes at The name is borrowed from the Go runtime, which shares and recycles memory on its own schedule. Keeping it stable needs a balanced tree of ranges, a clone when two ranges overlap, and a pin holding each backing alive.
A backing as a real VM object the identity of a heap object holding the bytes Every string comparison, concatenation and length check has to follow a pointer to a second object, on the VM's most common operations.
This pull request a serial number the VM hands out itself The string value grows from 16 to 32 bytes, and roughly twenty places that built a string by conversion have to build a struct instead.

What a mint looks like

StringValue stops being a Go string and becomes three fields.

  gnovm/pkg/gnolang/values.go

  before:  type StringValue string

  after:   type StringValue struct {
               Str    string   the text, exactly as before
               ID     uint64   which mint produced this backing; 0 = untracked
               Extent int64    how many bytes that whole backing holds
           }

NewString stamps a fresh ID from a single counter and sets Extent to the length. Copying a string copies all three fields, and slicing carries ID and Extent across unchanged while Str narrows. So every value over one backing agrees on its serial, and every one of them knows how big the whole backing is even when its own text is a ten-byte window into it.

  base := "aaaa … gggg"    512 bytes, one mint
  s    := base + base      1024 bytes, a new mint

                     Str                  ID      Extent
  base               "aaaa … gggg"        #41     512
  s                  "aaaa … gggg…"       #42    1024
  s1 := s            same text            #42    1024     copy: same serial
  s2 := s[1:11]      "aaaaaaaaaa"         #42    1024     slice: same serial,
                                                            still knows the
                                                            backing is 1024

The recount then keeps a set of serials it has already seen during this one walk. The first value carrying #42 adds a 48-byte header plus 1024 backing bytes; every later one adds the header alone. The set is thrown away when the walk ends, so the next collection counts everything again from zero.

Why the answer has to be the whole backing, not the visible text

This is the corner that decides between the designs, and alloc_13b.gno is the fixture that pins it. A program builds a 1024-byte string, keeps a copy and a ten-byte slice, and drops the original.

  s  := base + base   1024 bytes
  s1 := s             copy
  s2 := s[1:11]       slice
  s, base = "", ""    the source and the literal are gone
  runtime.GC()

All 1024 bytes are still held: Go cannot free a backing while any string points into it, so s2 alone keeps the whole thing alive. The recount reaches only s1 and s2, and both carry serial #42 and extent 1024, so it charges 1024 once.

DesignTimes the 1024 bytes are chargedWhy
Before this worktwiceEach surviving value is billed for the full backing.
A per-value "owner" flagneverThe owner died; the survivors are a copy and a slice, so nobody claims the bytes.
This pull requestonceTwo values, one serial, one charge, extent taken from the backing rather than from the ten bytes s2 shows.

The committed golden for that fixture is 8920 bytes after collection. The two failure rows are the shapes the fixture is written to catch, not measurements of this branch.

Where identity comes from after a restart

Serial numbers are not written to disk. Amino stores a StringValue as the plain text it always stored, so the on-disk format does not change and no migration is needed. A string read back from the store therefore arrives with serial 0, and the load path mints it again.

  gnovm/pkg/gnolang/realm.go, fillTypesOfValue

  before:  case StringValue: return cv              uncounted, forever
  after:   case StringValue: return store.GetAllocator().NewString(cv.Str)

The numbers themselves differ between two nodes, and between two runs on one node, because the counter is process-wide and never reset. What has to match across nodes is not the numbers but the grouping they induce: which values came from the same mint. That grouping follows from the order the VM executed, which is the same everywhere.

Strings the VM does not track

Serial 0 means untracked, and the recount charges those values a header and nothing else. It is a deliberate undercount, and it covers text the VM makes for itself rather than for the program: the message inside a runtime panic, and values built during uverse initialisation. The pull request moves several producers that user code can hold onto out of that category and into real mints.

ProducerBeforeAfter
String arguments of a MsgCall transactionuntracked, charged nothingminted through the transaction's allocator
The address and package path inside a realm handleuntrackedminted once, and Address() and PkgPath() hand back the very same value rather than a copy
A string loaded from the storeuntrackedminted on load
The text of a VM runtime panicuntrackedstill untracked

What this costs in gas

Allocation feeds gas, so an accounting change is a gas change, and the integration fixtures that assert exact gas all moved. The direction is upward, because the two large corrections in this branch both add: strings loaded from the store now cost something, and string literals that were previously hidden from the recount now enter it.

The one thing the new representation takes away

A Go string compares with == and two equal strings are equal. A three-field struct compares field by field, so two equal strings minted separately are now unequal, because their serials differ.

  StringValue{Str:"abc", ID:7,  Extent:3}
       ==
  StringValue{Str:"abc", ID:19, Extent:3}     false

Every comparison in the VM had to be checked against that. Most already went through GetString() and were unaffected. One did not: the compiler's check for a map literal written with the same key twice kept a set of the keys it had seen, using Go equality. It now keys that set the way the runtime keys a real map, by content.

  gnovm/pkg/gnolang/preprocess.go

  before:  kset := make(map[TypedValue]struct{})
  after:   kset := make(map[MapKey]struct{})
           mk, isNaN := cx.TypedValue.ComputeMapKey(nil, store, false)
