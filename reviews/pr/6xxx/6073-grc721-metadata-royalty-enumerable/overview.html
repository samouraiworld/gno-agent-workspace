What the branch adds

Three new packages under examples/gno.land/p/demo/tokens/grc721/, each a self-contained add-on to the core token that #6072 rewrites. A collection picks none, one, or all three. Nothing in the core changes here: the whole diff over #6072 is 12 new files, 1488 added lines, roughly 900 of them tests.

PackageWhat a holder or marketplace getsWhat it stores
metadata A URI per token, plus the OpenSea attribute fields (image, description, traits) held on chain instead of behind the URI. Two trees keyed by token id: one of URIs, one of metadata records.
royalty A cut of a sale price, in basis points, with a collection-wide default and per-token overrides under a cap fixed at construction. The default policy, the cap, and a tree of per-token overrides.
enumerable Counting and listing: how many tokens exist, the token at position N, and the Nth token of one owner. A list of every token id, a per-owner list, and three trees holding positions and owners.

How an extension attaches

The core splits a collection in two: a Token, which anyone may read, and a PrivateLedger, which only the issuing realm holds and which is the only way to mint, burn or move a token. Each extension constructor takes that private ledger, so attaching one is an issuer-only act, and hands back the same split: a read view for callers and a ledger for the issuer.

enum, enumLedger := enumerable.NewEnumerable(coreLedger)
meta, metaLedger := metadata.NewMetadata(coreLedger)
roy,  royLedger  := royalty.NewRoyalty(coreLedger, 1000)  // cap: 10%

Behind that call the constructor registers itself on the core as a hook set. Every movement the core performs then fans out to every attached extension, in registration order:

PrivateLedger.Mint(to, id)
  writes balance, owner, totalSupply
  emits Transfer(from: "", to, id)
  |
  +--> enumerable.OnMint   appends id to the global list and to to's list
  +--> metadata.OnMint     nothing
  +--> royalty.OnMint      nothing

PrivateLedger.transfer(from, to, id)      PrivateLedger.Burn(id)
  ... same shape ...                        ... same shape ...
  +--> enumerable.OnTransfer                +--> enumerable.OnBurn  drops id from both lists
  +--> metadata.OnTransfer  nothing         +--> metadata.OnBurn    drops uri and metadata
  +--> royalty.OnTransfer   nothing         +--> royalty.OnBurn     drops the per-token override

The hook set is a trust grant, and #6072 documents it as one: the issuer's code runs on every movement, and a panic inside it stops the movement. Only the issuer can attach a hook, since only the issuer holds the private ledger.

Who may write what

OperationNeeds
Set a token URI or its metadata recordThe metadata ledger, so the issuer
Set the default royalty, a per-token royalty, or clear eitherThe royalty ledger, so the issuer
Read a URI, a royalty, a count, a token at an indexNothing; the read views are public
Write anything through the enumerable ledgerNo such call exists: enumerable writes only from core hooks

A holder cannot rewrite the metadata or zero the royalty on a token they just bought, which is the property the issuer-only split is there for.

Royalty arithmetic

The royalty is basis points of the sale price: 10000 basis points is the whole price, 500 is 5%. The amount is salePrice * bps / 10000 in 64-bit integers, so it truncates rather than rounds, and a per-token override wins over the collection default. A sale price large enough to overflow the multiplication is refused rather than wrapped.

The box mirrors the branch's own expression. Checked against a run of the package on this head: at 1 basis point a price of 9999 pays 0, 10000 pays 1, and 19999 pays 1; at 10000 basis points a price of 922337203685477 pays itself and one more is refused as an overflow.

Enumerable, and why removal reorders

Removing a token from the middle of a list would cost a walk of everything after it, so the packages move the last id into the freed slot and cut the list short. That keeps every removal cheap and leaves the position of one other token changed:

global list   [1, 2, 3, 4]        burn 2
              [1, 4, 3]           4 has moved from position 3 to position 1

So a position is a cursor for one read, never a name for a token. A reader paging through with the index while a burn lands can see a token twice or miss one, exactly as the same design does elsewhere.
