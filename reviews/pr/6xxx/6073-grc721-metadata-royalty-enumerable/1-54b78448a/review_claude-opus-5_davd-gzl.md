## Overview

The branch adds three add-on packages to the NFT core that [#6072](https://github.com/gnolang/gno/pull/6072) rewrites: `metadata` for a per-token URI and an on-chain attribute record, `royalty` for a sale cut in basis points with a collection default and per-token overrides, and `enumerable` for counting and listing tokens. Each takes the core's `PrivateLedger`, which only the issuing realm holds, and registers itself as a hook set the core calls on every mint, transfer and burn. Each hands back two values: a read view anyone may hold, and a ledger the issuer keeps for writes. A collection attaches none, one or all three, which is what the title means by stackable. The core itself is untouched, so the reviewable work is 12 new files and 1488 added lines, roughly 900 of them tests.

**Verdict: REQUEST CHANGES** — six of the seven Warnings are states the code accepts in silence, an extension attached one mint too late, a metadata record rewritten through the read view, a royalty the event stream calls cleared while the chain still charges it, and one extension instance serving two collections; the seventh is measured, since `enumerable` keeps its lists as persisted slices and its share of a mint grows from **1.45M gas at 100 tokens to 7.26M at 4000** (7 Warnings, 5 Nits, 4 Suggestions, 1 missing test).

## Summary

Three packages, one shape: a constructor takes the core ledger, registers a hook set, and returns a read view plus an issuer ledger. `metadata` and `royalty` keep their own per-token records and validate every write against `core.OwnerOf`; `enumerable` instead mirrors ownership into its own lists and trees and never consults the core again, which is why every ordering defect lands there. The defects are not in the swap-and-pop arithmetic, which holds over a 400-step churn, but at the seams: the constructor accepts a core that has already minted, the hook methods are exported and accept any argument, one extension instance can be registered on a second core, and `metadata` hands out a struct whose one slice field still points at stored state.

Reading order: [`enumerable/token.gno`](https://github.com/jinoosss/gno/blob/refactor/grc721-extensions/examples/gno.land/p/demo/tokens/grc721/enumerable/token.gno#L64-L80) · [↗](../../../../../.worktrees/gno-review-6073/examples/gno.land/p/demo/tokens/grc721/enumerable/token.gno#L64) first, since it carries all the mutable index state, then [`royalty/token.gno`](https://github.com/jinoosss/gno/blob/refactor/grc721-extensions/examples/gno.land/p/demo/tokens/grc721/royalty/token.gno#L77-L87) · [↗](../../../../../.worktrees/gno-review-6073/examples/gno.land/p/demo/tokens/grc721/royalty/token.gno#L77) for the resolution order, then [`metadata/token.gno`](https://github.com/jinoosss/gno/blob/refactor/grc721-extensions/examples/gno.land/p/demo/tokens/grc721/metadata/token.gno#L39-L46) · [↗](../../../../../.worktrees/gno-review-6073/examples/gno.land/p/demo/tokens/grc721/metadata/token.gno#L39), which is the smallest of the three.

  `metadata` returns a sentinel error and also offers `HasTokenURI` and `HasMetadata`, `royalty` returns a bool, `enumerable` returns `ErrIndexOutOfRange`. `royalty` validates its receiver while `metadata` accepts any string as a URI: measured at this head, `SetTokenURI("1", "")` returns no error and `HasTokenURI` then answers true, against [EIP-721](https://eips.ethereum.org/EIPS/eip-721)'s requirement that a token URI be an RFC 3986 URI. `TokenURI` also answers `ErrNoTokenURI` for a token that was never minted and for a minted token with no URI, which the EIP separates. ## Verified

- Swap-and-pop arithmetic holds under churn: 400 deterministic steps, 106 mints, 156 transfers and 100 burns over four owners and seven reusable ids, asserting after every one of them that the extension's supply equals the core's, that every global position resolves to a live token, that each owner list is exactly as long as that owner's core balance, and that the owner lists sum to the supply. Green, in [`enumerable_churn_test.gno`](tests/enumerable_churn_test.gno).
- All three attached to one core behave: a transfer keeps the URI and the override, one burn clears the URI, the override and the index entry while the collection default survives, and a re-mint of the same id carries no URI, no override and one fresh index entry, resolving to the collection default. Run in [`enumerable_stack_test.gno`](tests/enumerable_stack_test.gno).
- A second `NewEnumerable` on the same core panics with the core's kind collision, so nothing in these packages reaches the uncomparable-interface fault reported on [#6072](https://github.com/gnolang/gno/pull/6072). Both extension types are pointers.
- A cross-realm write through the returned `Data` stops at the readonly taint, measured in [`metadata_alias_crossrealm_filetest.gno`](tests/metadata_alias_crossrealm_filetest.gno). That is what bounds the second Warning to the owning realm.
- Royalty truncation and bounds: 1 bps on a sale of 9999 pays 0 and on 10000 pays 1; `maxBps` 0 admits only 0; a negative sale price is refused. [EIP-2981](https://eips.ethereum.org/EIPS/eip-2981) blesses truncation in either direction.
- Storage deposit is flat in collection size: the byte delta of one mint is +8,706 at 100 tokens and +8,864 at 4000 with `enumerable` attached, against +2,130 and +2,202 with the core alone, and a burn refunds most of it. The four extra AVL nodes per mint are the whole difference.

## Open questions

- `RoyaltyInfo` answers for an id that was never minted and for one that was burned, returning the collection default, while `SetTokenRoyalty` on the same id refuses with `ErrTokenNotMinted`. OpenZeppelin's ERC-2981 skips the existence check too, so this matches the reference rather than diverging from it; the asymmetry between the read and write paths is worth one sentence in the `RoyaltyInfo` doc. Not posted, since no caller in the series passes an unvalidated id.
- `Trait.Value` is a string, so a numeric or date attribute can only ever be emitted quoted, which the OpenSea standard treats as a string trait. That only bites once something renders `Data`, which nothing does yet.
- `maxBps` is fixed at construction with no setter, and 0 is the parameter's zero value, so a collection deployed with an unset config field can never charge a royalty. A setter is a design decision for the author rather than a defect.
