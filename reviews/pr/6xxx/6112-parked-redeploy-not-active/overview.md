# gpao's pre-flight and the two places a package can live

Generated by claude-opus-5.

## TLDR

A gno.land chain running the `inert` code submission policy stores a submitted
package without activating it. gpao is the daemon that typechecks those parked
packages off-chain and sends the `MsgEnablePackage` that activates them. Before
sending one it asks the chain whether the work is already done, and it asked a
query that can only see activated packages. A private realm can be live and
have a redeploy parked over it at the same time, so that query answered "already
live" for a path with a redeploy still waiting, and gpao recorded success for a
message it never sent.

## Two key spaces

A gno.land node keeps parked packages under their own key prefix, separate from
the live ones. Nothing moves between the two until an approver enables the
parked blob, at which point
[`EnablePackage`](https://github.com/gnolang/gno/blob/2ed70a202e6f92364be56c5c17ddd706e0c9d922/gno.land/pkg/sdk/vm/keeper_inert.go#L367)
deletes it from the parked space.

Most queries read the live space alone. That is why
[`QueryPackageMeta`](https://github.com/gnolang/gno/blob/2ed70a202e6f92364be56c5c17ddd706e0c9d922/gno.land/pkg/sdk/vm/keeper_inert.go#L519)
exists: it reads both and reports a `status` plus a
[`Pending`](https://github.com/gnolang/gno/blob/2ed70a202e6f92364be56c5c17ddd706e0c9d922/gno.land/pkg/sdk/vm/keeper_inert.go#L496-L503)
flag.

## What the chain can hold at one path

`AddPackage` refuses to park over a live package only when the live one is
[public](https://github.com/gnolang/gno/blob/2ed70a202e6f92364be56c5c17ddd706e0c9d922/gno.land/pkg/sdk/vm/keeper.go#L730),
so "live" and "has a submission waiting" coexist for a private realm.

| live blob | parked blob | `vm/qfile` | `vm/qpkgmeta_json` | is there an enable to send |
| --- | --- | --- | --- | --- |
| none | none | error | `status: absent` | no, nothing is there |
| none | yes | error | `status: inert, pending: true` | yes |
| yes | none | answers | `status: live` | no |
| yes, private | yes | answers | `status: live, pending: true` | yes, and this is the case that was dropped |

The bottom row is the whole subject. `vm/qfile` answers from the live blob, so
it is indistinguishable from row three.

## What the daemon does with that answer

```
block carries MsgAddPackage
        |
        v
   typecheck off-chain
        |
        v
   pre-flight: is there anything to enable?
        |                          |
     nothing                   something
        |                          |
        v                          v
  record "already active"    simulate, then broadcast MsgEnablePackage
```

Before this change the pre-flight was `isActive`, a `vm/qfile` probe: any
successful answer meant settled. After it, the pre-flight is `isSettled`, a
`vm/qpkgmeta_json` probe, and only `status: live` with no `pending` counts as
settled. Every other answer, a query failure and unparsable data included, sends
the enable, so a node that cannot answer never stops the daemon approving.

## What a redeploy costs a submitter today

Numbers below are from a run of the daemon's own code against an in-memory
gno.land node holding the `inert` policy, not from a model of it. The harness is
`casespace_test.go` in the review directory.

| the chain at the path | old pre-flight | new pre-flight | what the daemon does |
| --- | --- | --- | --- |
| nothing submitted | not settled | not settled | tries, the simulate refuses it |
| parked, never enabled | not settled | not settled | enables it |
| live, nothing waiting | settled | settled | skips it |
| live private, redeploy waiting, and the redeploy is the candidate | settled | not settled | enables it |
| live private, redeploy waiting, and the candidate is the older live blob | settled | not settled | tries, the simulate refuses it |

Row four is the fix. Row five is what it costs: replaying an old block at a path
whose parked bytes are newer now attempts an enable the chain will refuse.
