grc721 rewritten on the Token / PrivateLedger / Teller axis

Plain-language overview of gnolang/gno PR 6072 (1 of 4)  ·  generated by claude-opus-5  ·  explainer only, no review verdict

An NFT library on gno lets a realm issue non-fungible tokens: unique items with an owner, transfers, and approvals, the same shape Ethereum calls ERC-721. This PR replaces the old BasicNFT library under p/demo/tokens/grc721 with three smaller types, and moves the four in-repo realms that used the old one onto the new one in the same change so nothing in the tree breaks.

Why the old shape was hard to use safely

The library predates gno's current rule for how one realm proves who is calling it. Three things followed from that:

Who-is-calling was an argument

Every write took a caller address. The calling realm asserted its own identity, and each realm re-wrote the same check. Nothing tied that address to the call actually arriving.

One handle did read and write

A single *BasicNFT value carried both the getters and the mutators, so handing it to another realm to let it read also let it write.

Extras were built in

Metadata and royalty lived in the core package, so every collection carried their storage and gas cost whether it used them or not.

It diverged from the fungible library

The fungible-token library grc20 had already settled on a Token / Ledger / Teller split. grc721 doing something else meant learning two mental models for one problem.

The three new types

TypeWhat it isWho holds it
TokenThe read view: name, symbol, supply, owner-of, approvals. No method changes state.The handle a realm exposes for queries.
PrivateLedgerThe write authority: Mint, Burn, Approve, TransferFrom, and RegisterExtension.Only the issuing realm. NewToken returns it once and it is never handed out.
TellerA capability that performs a write as some account. It carries no balance of its own; it names whose authority a write runs under.Created in one of five grades below.

A collection creates a token like this:

token, ledger := grc721.NewToken("Foo NFT", "FNFT", 0, cur)
// token  -> the read view, safe to expose
// ledger -> the write authority, kept private to this realm

The five teller grades

A Teller answers one question when it writes: which account is this write charged to? The grade fixes the answer.

GradeActs as
CallerTellerWhoever crossed into the realm that calls the write, resolved fresh on every call.
ReadonlyTellerNobody. Every write returns ErrReadonly.
RealmTellerThe realm that built it, fixed at build time.
RealmSubTellerA sub-account of the building realm, derived from a slug string.
ImpersonateTellerAn arbitrary address the issuer names. Admin-grade, issuer only.

Every writing teller re-checks that the realm value passed to it is the live crossing frame (rlm.IsCurrent()) and rejects it with ErrSpoofedRealm otherwise. IsCanonicalTeller confirms a teller value was minted by the package rather than forged by embedding, but it does not reveal which of the five grades it is.

How a write flows

caller realm grc721 (p/demo/tokens/grc721) ------------ ----------------------------- foo721.TransferFrom(cur, ...) | | teller.TransferFrom(0, cur, from, to, tid) v +----------------+ rlm.IsCurrent()? --no--> ErrSpoofedRealm | fnTeller | | accountFn(rlm)| --> resolves the acting account (grade-specific) +-------+--------+ | ledger.TransferFrom(spender, from, to, tid) v +----------------+ spender owns or is approved for tid? | PrivateLedger | --no--> ErrCallerIsNotOwnerOrApproved | owners/bal/ | | approvals AVL | --yes--> move tid, emit Transfer, run extension hooks +----------------+

Two behaviour changes worth knowing

A NewToken event on every creation

Because a Token's fields are private, NewToken is the only way one can exist, so the event it emits sees every token that will ever emit. A caller supplies the trailing number, so one realm can build two tokens with the same identifier; an indexer that sees the same id announced twice knows to stop trusting that realm's events. The filetests/newtoken_event_filetest.gno fixture demonstrates the duplicate.

Approve(zero) now clears an approval

ERC-721 clears a single-token approval by approving the zero address. The old code rejected the zero address, leaving no way to revoke without transferring. The new Approve treats the zero address as a revoke.

What this PR removes

BasicNFT, NewBasicNFT, the IGRC721 reader/writer interfaces, and the in-package metadata and royalty files are deleted. This is a breaking change to a p/demo/ package. The PR notes the package is not in the current testnet genesis set and every user in the tree lives under examples/quarantined/, so the reach is limited to this repository. Metadata, royalty, enumerable, a read-only collection handle, and a discovery registry return in the later three PRs of the series (6073, 6074, 6075).
