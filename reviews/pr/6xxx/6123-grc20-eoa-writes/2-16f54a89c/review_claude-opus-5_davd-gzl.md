## Overview

A GRC20 token decides whose balance a write touches by picking a *teller*. Round 1 added [`UserTeller`](https://github.com/gnolang/gno/blob/16f54a89c/examples/gno.land/p/demo/tokens/grc20/tellers.gno#L44-L56) on the private ledger, confined to the token's own realm, and let a token name relays it would serve. This round deletes the relay list and moves the constructor onto the published `*Token`, so it takes no arguments, carries no `homeGuard`, and needs nothing from the token realm. The single condition left is [`rlm.Previous().IsUserCall()`](https://github.com/gnolang/gno/blob/16f54a89c/examples/gno.land/p/demo/tokens/grc20/tellers.gno#L152-L155), which asks whether the frame that called the realm holding the teller is a signing account rather than a contract, and the branch's new [ADR](https://github.com/gnolang/gno/blob/16f54a89c/gno.land/adr/pr6123_grc20_eoa_entrypoints.md?plain=1#L36-L40) records that a realm a user calls directly may then transfer or approve that user's tokens with no prior allowance. [`grc20reg`](https://github.com/gnolang/gno/blob/16f54a89c/examples/gno.land/r/demo/defi/grc20reg/grc20reg.gno#L145-L158) gains `UserTransfer`, `UserApprove` and `UserTransferFrom` on top of it. Tests come as gno unit tests, two filetests, the fixture realm carried from round 1, and six scripted integration chains.

**Verdict: REQUEST CHANGES** — the gate admits `MsgAddPackage` where [`tellers.gno:39`](https://github.com/gnolang/gno/blob/16f54a89c/examples/gno.land/p/demo/tokens/grc20/tellers.gno#L39) requires a direct `MsgCall`, so a newly deployed realm's `init(cur realm)` moves the deploying account's whole balance, and `Approve`, `TransferFrom` and `IsCanonicalTeller` each reach past the bounds the ADR states, all four new in this branch (4 Warnings, 1 missing test, 4 suggestions, 2 nits, 4 not posted).

## Summary

Round 1's design was closed by default: a foreign realm could act for a holder only after the token's own realm named it, and even a leaked teller was inert away from home. This round's design is open by default, and the [ADR](https://github.com/gnolang/gno/blob/16f54a89c/gno.land/adr/pr6123_grc20_eoa_entrypoints.md?plain=1#L36-L40) states that and accepts it. `Token.UserTeller()` hangs off the published pointer with no host list, no `homeGuard` and no per-token switch, so the capability round 1 said a token grants to one named realm is one every realm now holds against every user who calls it directly. [`MustGet`](https://github.com/gnolang/gno/blob/16f54a89c/examples/gno.land/r/demo/defi/grc20reg/grc20reg.gno#L71-L76) and [`GetRegistry`](https://github.com/gnolang/gno/blob/16f54a89c/examples/gno.land/r/demo/defi/grc20reg/grc20reg.gno#L204-L206) hand that pointer to any caller, so registering a token and delegating spend authority over its holders are now one act, and [`wugnot`](https://github.com/gnolang/gno/blob/16f54a89c/examples/gno.land/r/gnoland/wugnot/wugnot.gno#L15-L29) gets it without its author touching a line. That much is the decision, and it is the first Suggestion below.

What the branch gets right is the predicate. The gate uses the strict [`IsUserCall()`](https://github.com/gnolang/gno/blob/16f54a89c/gnovm/stdlibs/chain/runtime/frame.gno#L105-L107) rather than `IsUser()`, and a `MsgRun` script is genuinely refused even when the script builds the teller itself, which the branch's own [`grc20_registry_user_relay.txtar:125-126`](https://github.com/gnolang/gno/blob/16f54a89c/gno.land/pkg/integration/testdata/grc20_registry_user_relay.txtar#L125-L126) asserts and this round re-ran green. The gate is required rather than rejected on, which is the correct side of the test. Where the code parts from the document is `MsgAddPackage` walking that gate, plus three write paths the ADR's bounds paragraph does not name: a standing allowance that outlives the call, an allowance a third party granted the caller, and a canonical-teller check that clears a value debiting the validating realm's own caller. All four are caused by this branch and all four ship to users.
